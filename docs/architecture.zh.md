# 架构

[English](architecture.md)

## 不可变计划

`Prepare` 在创建运行环境前解析源码并校验配置。调用方保存 `plan.Snapshot()` 和 `plan.ConfigBytes()` 的副本；`Restore` 重新校验原始 YAML 的摘要与协议，不访问源码服务。执行计划不会再次解析原来的分支。

`Source` 将固定版本解析与空目录中的源码落地分开；`Runtime` 将有限命令、独立进程、检查、停止和就绪入口分开。进程引用包含运行时、进程和唯一执行标签。凭证只保留在适配器或临时 `Options.Env` 中。

## 执行

1. `preparing`：排他创建 `WorkRoot/OperationID`。已有路径返回 `ErrConflict`，不删除或复用目录。
2. `cloning`：拉取并检出已保存的完整提交。
3. `verifying`：校验配置摘要、普通文件要求，以及配置与工作目录的物理路径位于工作区内。
4. `installing`：带临时环境变量执行安装或构建命令。
5. `starting`：安装后重新检查配置和目录，确认前台服务进程已独立启动，且运行时与操作标签匹配。
6. `probing`：检查进程存活，轮询就绪入口与健康路径。只接受 HTTP 2xx，不跟随重定向，成功后再次检查进程。配置的就绪期限最多 300 秒。
7. `ready`：返回 UTC 就绪时间以及源码和进程证据。

`OnStage` 在每个阶段产生副作用之前执行，可以持久化阶段确认。随后 `OnCheckpoint` 接收部分结果的副本，从 `starting` 开始还包含只有标签的 `StartIntent`；返回前必须完成持久化确认。`probing` 包含已确认进程，`ready` 还包含入口与 UTC 就绪时间。回调失败会停止推进，并补偿清理已启动进程；就绪确认失败时返回结果不含 `ReadyAt`。默认拉取期限为 5 分钟，安装为 15 分钟，准备、校验和启动各 1 分钟，补偿性进程清理为 5 秒。调用方取消也会约束执行。成功启动的服务生命周期独立于 Apply context。

## 失败与生命周期

即使 Apply 返回错误也应保存 `Result`。`StageError` 提供失败阶段，`errors.Is` 保留原因和清理失败类型；其打印信息不包含命令、YAML 或服务端响应体。启动失败可能返回只有标签的进程引用；若丢失 PID 确认，运行时可以按唯一标签检查或停止。不要复用操作标识或标签，同一次尝试的动作必须串行执行。

不确定或已确认启动之后发生失败时，会用独立且有期限的 context 尝试停止进程，包括调用方 context 已取消的情况。清理错误保留在 `StageError.Cleanup`，由应用负责后续核对。库不实现持久化编排、分布式租约、原子 fencing、脚本自动重试或恰好一次执行。

`Stop` 只终止保存的应用执行。工作目录保留供调用方诊断和管理，运行时不会被销毁。就绪服务持续运行，直到主动停止、运行时关闭或进程退出。就绪既不证明公网入口可用，也不持续监控服务健康。

## 输出

每阶段两个流合计保留最多 64 KiB 原始输出。阶段结束回调前先合并各流，再替换显式 `Redact` 值和临时环境变量值，覆盖跨传输分块的完整秘密值。事件是最多 4 KiB 的有效 UTF-8 文本，先 stdout 后 stderr，必要时附截断标记，不保留精确交错顺序。确认 PID 后结束启动观察，阶段结束后的迟到输出被丢弃。

脱敏匹配覆盖重叠的秘密值，也会隐藏截断边界处可能构成凭证开头的不完整后缀，避免裁剪完整凭证后泄露其前缀。

回调必须及时返回。仓库输出是不可信文本，应以纯文本渲染。脱敏只覆盖传入的字面值，不识别任意变换后的秘密。持续日志订阅和事件持久化由应用负责；配置与命令不应嵌入凭证。

## 控制器接管

将检查点保存到尝试日志，与配置字节和临时凭证分开。崩溃后先取得排他所有权，重建同一运行时实例，再核对并停止 `Result.Process`；丢失响应时使用 `StartIntent`。启动意图不证明进程存在，也不证明冲突启动拥有现存进程。不得复用标签或清理其他尝试。

`Restore` 恢复计划，不恢复执行游标。已有工作区上再次调用 `Apply` 会返回 `ErrConflict`。完成核对后才能决定是否使用新操作标识重新运行脚本；安装的外部副作用可能使重放不安全。库不阻止失效 Worker，也不持久化失败和清理完成状态；除检查点外，还应保存最终部分结果与 `StageError.Cleanup`。参见[可编译接管示例](../recovery_example_test.go)。
